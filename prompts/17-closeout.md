# 17. 마무리

첫 마일스톤이다. 세 엔진 전체를 돌리고, 문서를 코드에 맞추고, 결과를 보고서 하나로 남긴다.

| 항목 | 값 |
| ---- | -- |
| 브랜치 | `stage/17-closeout` |
| 선행 | 16 (고친다로 정한 결함이 모두 닫힘이거나 알려진 버그) |
| 읽을 문서 | DESIGN 전체, `docs/` 전체, 모든 `POLICY.md` |
| 고칠 폴더 | `docs/`, `README.md`. 코드는 고치지 않는다 |
| 쓸 스킬 | (설치하면) `work-closeout`, `affected-verification` |

## 이 단계가 끝나면

- [ ] `bun run check`, `bun run test:e2e:all`, `bun run build`, `bun run test:e2e:build`가 한 번에 모두 종료 코드 0이다. 돌린 시간을 `docs/test-plan.md`에 적었다.
- [ ] 개발 데이터로 `bun run data:check`가 어긋남 0이다.
- [ ] DESIGN.md가 코드와 맞는다. 폴더 구조(8장), API(4장과 `docs/API.md`와 계약 패키지), 정책 표(9장과 각 `POLICY.md`)를 맞대 본 결과가 있다.
- [ ] 모든 `POLICY.md`가 "승인"이고, `AGENTS.md` 9장의 상태 표가 같다.
- [ ] `docs/DECISIONS.md`에 그동안의 결정과 따르지 않은 AI 제안이 있다.
- [ ] `docs/REPORT.md`가 프롬프트 2의 구성이고, 맨 앞에 읽는 법과 숫자가 있다. 사람이 확인하지 않은 주장과 근거 없는 추정이 없다.
- [ ] 개선 후보까지 모두 "한다"나 "안 함"으로 정해졌다. 직접 확인 목록에 "하지 않음"이 남지 않았다.
- [ ] 화면 캡처(`docs/evidence/ui/`)를 마지막 상태로 다시 찍었고, 보고서가 그 캡처를 쓴다.
- [ ] 폴더마다 설명 준비(프롬프트 3)를 했고, `docs/QA.md`(프롬프트 4)가 있고, 사람이 그 자리 수정 리허설을 했다.
- [ ] `README.md`가 처음 보는 사람이 5분 안에 앱을 띄울 수 있게 쓰였다.

## 순서

1. **입력** 프롬프트 1(전체 확인).
2. **확인** 사람이 같은 명령을 PowerShell에서 한 번 더 돌린다. 시간이 오래 걸리니 다른 일을 하지 않는 때에 돌린다.

   ```powershell
   bun run check
   bun run test:e2e:all
   bun run build
   bun run test:e2e:build
   bun run data:check
   ```

3. **사람** 직접 확인 목록에서 "하지 않음"으로 남은 것을 한 번에 한다. 판정 기준이 없는 항목은 목록에서 빼고 "측정과 테스트로 갈음"이라고 적는다.
4. **입력** 프롬프트 2(문서 맞추기와 보고서). 보고서를 먼저 쓰고, 그다음 작업용 문서를 정리한다.
5. **사람** `docs/REPORT.md`를 읽는다. 사람이 확인하지 않은 주장(예: "실제 Safari에서 된다")이나 근거 없는 추정(예: "손으로 하면 몇 달")이 있으면 지우게 한다.
6. **입력** 프롬프트 3(설명 준비). **사람** 결과를 읽고 자기 말로 다시 쓴다. 블로그 글이나 정리 문서로 남기면 포트폴리오의 근거가 된다.
7. **입력** 프롬프트 4(질문과 리허설). **사람** 리허설 문제를 손으로 한 번, 에이전트와 한 번 한다. 리허설은 `rehearsal/{이름}` 브랜치에서 하고 반영하지 않는다.
8. **입력** 반영 프롬프트. 반영 뒤 태그를 달지 사람이 정한다(`git tag v1.0.0`).
9. **사람** 원격 저장소에 올리기 전에, 공개하면 안 되는 이름(회사, 사람, 내부 프로젝트)이 문서와 커밋 메시지에 없는지 직접 검색한다. 올리는 것은 사람이 한다.
10. **입력** (선택) 다른 사람에게 넘길 묶음이 필요하면 프롬프트 5.

## 프롬프트 1. 전체 확인

```text

테스트의 전체 출력은 시각을 붙인 로그 파일로 보내고, 대화에는 마지막 요약과 실패만 보인다.
마무리 단계다. 브랜치 stage/17-closeout 을 main에서 만든다. 코드를 고치지 않는다.

1. 다음을 차례로 돌리고, 명령마다 걸린 시간, 마지막 줄, 종료 코드를 표로 보인다.
   bun run check, bun run test:e2e:all, bun run build, bun run test:e2e:build, bun run data:check
2. 하나라도 실패하면 멈추고 보고한다. 다시 돌려서 넘기지 않는다. 연결 거부나 시간 초과는 그 파일만 한 번 다시 돌리고 두 결과를 모두 적는다.

4. 엔진별 통과, 실패, 건너뜀 수와 시간을 docs/test-plan.md 의 "잰 시간" 표에 더한다. 잰 날짜와 PC(코어 수, 메모리, 워커 수)를 함께 적는다.
```

## 포트폴리오로 옮길 것

17단계가 끝나면 이 폴더의 [TASKS.md](../TASKS.md)의 N2(포트폴리오 소개)를 쓸 재료가 모인다. 틀은 이렇다.

- **한눈에:** 처음과 지금을 나란히 둔 표. 숫자는 직접 센다.
- **여러 역할:** 프론트엔드, 기능 제안, API와 데이터 설계, AI 활용을 각각 어디서 보이는지 하나씩 짚는다.
- **흐트러지지 않는 구조:** 정책, 테스트 먼저, 검증 루프가 새 기능에서도 지켜진 예. 규칙을 바꿔 넣은 기능(12단계)의 흐름.
- **Trade-off와 한계:** DECISIONS.md 와 고치지 않은 것에서.
- **사람의 몫:** 사람이 정한 규칙, 뒤집은 AI 제안, 사람이 직접 쓴 설명(블로그 글이나 정리 문서)을 근거로 건다.
- **한 줄의 줄기:** 이 작업을 한 문장으로 줄인다. 예: "구현은 에이전트에게 맡기고, 기준은 문서와 테스트로 저장소에 두었다". 그 문장에서 시작해, 왜 기준이 저장소에 있어야 했고 왜 테스트가 먼저였는지를 순서대로 쓴다.
- 주장은 근거 링크가 있을 때만 쓴다.

## 막히면

- **세 엔진 전체가 한 번에 통과하지 않는다.** 실패를 다시 돌려 넘기지 않는다. 그 실패를 16단계의 결함으로 등록하고 고친 뒤 다시 이 단계를 한다.
- **"하지 않음"이 남는다.** 절차와 기대 결과를 적을 수 없는 항목이면 목록에서 빼고 "측정과 테스트로 갈음"으로 적는다. 적을 수 있으면 사람이 한다. 남겨 두면 할 수 있었는데 안 한 것으로 읽힌다.
- **보고서가 길어진다.** 장마다 다섯 줄 안쪽으로 줄이고 자세한 것은 링크한다. 읽는 사람은 근거를 따라가 볼 수 있으면 된다.
