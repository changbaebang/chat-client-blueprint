# 16. 결함 고치기

15단계의 `docs/Issues.md`에서 "고친다"로 정한 결함을 묶음마다 고친다. `docs/Improvements.md`에서 "한다"로 정한 개선도 같은 방식으로 묶는다. 묶음 하나가 브랜치 하나다. 이 단계는 결함 수만큼 되풀이한다.

| 항목 | 값 |
| ---- | -- |
| 브랜치 | 묶음마다 `fix/{BUG-ID들이나 짧은 이름}` |
| 선행 | 15 |
| 읽을 문서 | `docs/Issues.md`의 그 행, 고칠 폴더의 `POLICY.md`, [DESIGN 9.14절](../docs/DESIGN.md#914-정책을-바꾸는-절차), [11.2절](../docs/DESIGN.md#112-작성-규칙) |
| 쓸 스킬 | (설치하면) `bug-triage`, `side-effect-check`, `affected-verification`, `critical-review` |

## 묶는 기준

- 같은 파일이나 같은 원인을 건드리는 결함은 한 묶음이다.
- 묶음 하나는 반나절 안에 끝나는 크기다. 넘으면 나눈다.
- 순서는 `docs/Issues.md`의 순서(심각도, 비용)다. 다른 결함을 고치면 사라질 결함은 뒤로 미룬다.
- 남은 일은 성질별로 나눈다: 결함, 개선, 문서. 시간이 모자라면 개선(새 기능)을 먼저 뺀다.
- 묶음이 셋을 넘으면 README 6.8절의 선언 지시로 묶음 목록과 끝나는 조건을 `docs/TASKS.md`에 먼저 옮긴다.

## 한 묶음의 순서

1. **사람** 묶음을 고르고 `docs/Issues.md`의 그 행들을 읽는다. 에이전트는 착수 전에 재현하거나 지금 상태를 확인한다. 재현 안 됨, 이미 해결됨, 전제가 틀림이면 구현하지 않고 근거와 함께 닫는다. 일부만 실제면 범위를 줄이고 기록한다. 원인이 흐리면 README 6.9절의 관찰 지시를 먼저 쓴다.
2. **입력** 프롬프트 1(재현 테스트). 테스트가 지금 코드에서 실패하는 것을 본다. 실패하지 않으면 그 결함은 재현되지 않은 것이다. 고치기 전에 실패하지 않으면 고치지 말고 멈춘다. 4번의 "재현되지 않음"으로 간다.
3. **입력** 프롬프트 2(고치기). 사람이 직접 고칠 때는 README 6.4절의 "위치 설명"을 쓰고 직접 고친다.
4. **확인**

   ```powershell
   bun run check
   bun --bun playwright test {재현 테스트 파일}
   bun run test:e2e
   ```

5. **입력** 검토 프롬프트. 절은 "Issues.md의 {BUG-ID들}과 고친 폴더의 POLICY.md".
6. **사람** `docs/Issues.md`의 상태를 확인한다. 고친 것은 "닫힘"과 커밋 해시, 고치지 않기로 바꾼 것은 이유와 영향.
7. **입력** 반영 프롬프트.

**재현되지 않음:** 다른 작업으로 이미 사라진 결함은 재현 테스트가 통과하는 것을 보이고, 사라지게 한 커밋과 한 줄 설명으로 닫는다. 테스트는 회귀 방지로 남긴다. 원인을 끝까지 밝히지 못했으면 "확인하지 못함"으로 적는다. 그것도 완료다.

**알려진 버그:** 고치지 않기로 한 결함은 재현 테스트에 `test.fail`(Playwright)이나 `test.failing`(bun test)를 달고, 위에 BUG-ID와 이유를 주석으로 쓴다. 표시한 테스트가 통과하기 시작하면 실패로 나오니, 그때 표시를 뗀다.

## 프롬프트 1. 재현 테스트

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 먼저 AGENTS.md와 docs/TASKS.md의 지금 상태를 읽고 AGENTS.md의 규칙을 따른다.
테스트의 전체 출력은 시각을 붙인 로그 파일로 보내고, 대화에는 마지막 요약과 실패만 보인다.
결함 {BUG-ID들}을 고치기 전에 재현 테스트만 쓴다. 앱 코드는 고치지 않는다.
브랜치 fix/{이름} 을 main에서 만든다.

1. docs/Issues.md 의 그 행들을 읽는다. 테스트 층은 그 행의 제안을 따르되, 맞지 않으면 DESIGN 11.1절의 기준으로 바꾸고 이유를 적는다.
2. 결함마다 지금 코드에서 실패하는 테스트를 쓴다. 테스트 이름은 고친 뒤의 올바른 동작으로 쓴다(결함의 설명이 아니라).
   응답 순서나 시간이 원인이면 page.route, 가짜 시계, mock 지시어로 순서를 고정한다. 고정 대기를 쓰지 않는다.
   늦게 온 응답이 원인이면 늦은 성공과 늦은 실패를 둘 다 쓴다. 붙잡은 요청은 테스트 끝에 끊는다.
3. 돌려서 실패하는 출력을 결함마다 보인다. 실패하지 않는 결함은 "재현되지 않음"으로 보고하고, 어떻게 재현하려 했는지 적는다.
   양방향 확인: 고칠 곳을 임시로 고쳐 테스트가 통과하는지 보고 되돌린다. 시작 전에 그 파일을 백업하고, 나에게 그 파일을 고치지 말라고 알린다.
   되돌린 뒤 cmp 로 백업과 같은지 보인다.
4. 표시 없이 커밋한다: "test: reproduce {BUG-ID들}". 브랜치에서는 실패해도 된다. main 에는 들어가지 않는다.
```

## 프롬프트 2. 고치기

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 먼저 AGENTS.md와 docs/TASKS.md의 지금 상태를 읽고 AGENTS.md의 규칙을 따른다.
고칠 폴더에 POLICY.md가 있으면 먼저 읽는다. "승인"인 정책만 규칙이다.
DESIGN.md나 승인된 정책과 부딪히거나, 되돌리기 어렵거나 다른 단계에 걸리는 판단이 필요하면 고치기 전에 멈추고 규칙 ID, 이유, 권장안을 보고한다. 그 밖의 작은 판단은 정한 뒤 보고의 "정한 것"에 적는다.
테스트의 전체 출력은 시각을 붙인 로그 파일로 보내고, 대화에는 마지막 요약과 실패만 보인다.
끝나면 AGENTS.md 12장의 형식으로 보고한다. 돌리지 않은 것과 확인하지 못한 것은 그렇다고 쓴다.

결함 {BUG-ID들}을 같은 브랜치에서 고친다. 재현 테스트는 앞 커밋에 있다.

1. 원인을 먼저 보고한다: 어느 파일의 어느 줄이, 어떤 입력에서, 왜 틀리는지. 코드에서 이유를 짚을 수 없으면 고치지 말고 멈춘다.
2. 원인만 고친다. 결함과 상관없는 정리나 이름 바꾸기를 섞지 않는다. 그런 것이 보이면 목록으로 보고만 한다.
3. 같은 모양의 문제가 다른 곳에 있는지 검색하고, 있으면 고치지 말고 보고한다(새 BUG 후보).
4. 재현 테스트가 통과하는 것을 보인다. 고친 줄을 되돌리면 다시 실패하는 것도 한 번 본다(변이 확인). 되돌리기 전에 백업하고, 다시 고친 뒤 cmp 로 같은지 보인다.
5. bun run check, bun run test:e2e 를 돌린다.
   같은 동작을 보는 e2e 를 덜어낼 때는, 그 동작을 깨는 변이로 남는 테스트가 실제로 실패하는지 본 뒤에 지운다.
6. docs/Issues.md 의 그 행을 "닫힘"으로 바꾸고 원인과 고친 내용을 한 줄로 적는다. 정책에 새로 알게 된 규칙이 있으면 9.14절의 절차로 제안만 한다.
7. "fix: {고친 뒤의 동작}" 으로 커밋한다.
```

## 막히면

- **고치려면 승인된 "반드시" 규칙을 어겨야 한다.** 멈추고 DESIGN 9.14절의 절차로 보고하게 한다. 사람이 승인하면 정책을 고친 커밋을 먼저 하고 그다음 코드를 고친다.
- **재현 테스트가 가끔만 실패한다.** 순서를 고정하지 못한 것이다. 무엇이 순서를 정하는지 찾을 때까지 고치지 않는다. 고정할 수 없으면 꼬리표를 달아 따로 돌리는 식으로 숨기지 말고 "확인하지 못함"으로 적는다.
- **`test.fail`을 달려는데 결과가 들쭉날쭉하다.** `test.fail`은 결과가 늘 같은 결함에만 단다(DESIGN 11.2절). 기기 속도에 따라 달라지는 것은 기록만 한다.
- **세 엔진 중 하나에서만 실패한다.** 그 엔진의 동작이 원인일 수 있다. DESIGN 7.3절의 표에 행을 더할지 사람이 정한다.
