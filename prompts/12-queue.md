# 12. 대기열 (선택)

건너뛰어도 13단계부터 그대로 돈다. 건너뛰면 `docs/TASKS.md`에 "안 함"과 이유를 적는다.

이 단계는 연습 둘을 겸한다. 하나는 새 기능의 상태 규칙을 사람이 직접 정하는 것(프롬프트 0), 다른 하나는 정책 변경 절차의 첫 연습이다([DESIGN 9.14절](../docs/DESIGN.md#914-정책을-바꾸는-절차)). 대기열은 이미 승인된 규칙이나 앞 단계의 스펙과 부딪히는 곳이 있다. 프롬프트 1은 그곳을 일부러 말하지 않는다. 에이전트가 스스로 찾아 멈추는지 본다.

| 항목 | 값 |
| ---- | -- |
| 브랜치 | `stage/12-queue` |
| 선행 | 11 |
| 읽을 문서 | [DESIGN 3.2절의 F-QUEUE](../docs/DESIGN.md#f-queue-대기열-선택-단계-12), [4.6절의 `duplicate_message`](../docs/DESIGN.md#46-답변-스트림), [7.1절](../docs/DESIGN.md#71-상태), [9.11절의 STATE-12](../docs/DESIGN.md#911-srcstate) |
| 고칠 폴더 | `src/state/queue-rules.ts`, `state/chats.tsx`, `components/chat` |
| 쓸 스킬 | (설치하면) `react-review` |

## 이 단계가 끝나면

- [ ] 답변 중에도 입력창이 열려 있고, Enter는 대기열에 쌓는다. 채팅마다 차례대로 보낸다. 다른 채팅을 보는 동안에도 보낸다.
- [ ] 항목마다 취소가 있다. 중단과 실패는 대기열을 멈추고 입력창 위에 "N queued", Send, Clear를 보인다.
- [ ] 멈춘 대기열에 보낸 메시지는 끝에 쌓인다.
- [ ] 다음 메시지는 답변이 끝난 이벤트가 아니라 연결이 닫힌 뒤에 보낸다.
- [ ] 같은 `clientMessageId`의 409 `duplicate_message`는 "이미 받음"으로 보고 서버와 맞춘다.
- [ ] 대기열 전이는 순수 함수이고 모듈 테스트가 있다. 변이를 넣어 테스트가 실패하는 것을 봤다.
- [ ] 대기열의 상태 규칙을 사람이 정했다. 확정 표, 제약, 하지 않는 것이 `docs/DECISIONS.md`에 "사람이 정함"으로 있다.
- [ ] 거절된 메시지는 뒤에 대기가 있으면 맨 앞으로, 없으면 입력창으로 간다. 빈 대기열은 멈춘 것으로 보이지 않는다.
- [ ] 정책 변경 연습의 결과(에이전트가 스스로 멈췄는지, 정책 커밋이 코드보다 먼저인지)가 `docs/TASKS.md`의 이 단계 메모에 있다.

## 순서

0. **입력** 프롬프트 0. 에이전트가 질문 목록을 내고 멈춘다. **사람** 항목마다 답한다. 이 답이 이 기능의 상태 규칙이다.
1. **입력** 프롬프트 1. **사람** 에이전트가 승인된 규칙이나 스펙과 부딪히는 곳을 스스로 찾아 멈추는지 본다. 멈추면 9.14절대로 정책 커밋을 먼저 하게 한다. 멈추지 않고 넘어갔으면 절차의 빈틈으로 `docs/TASKS.md`에 적고, 그 자리에서 멈추게 한 뒤 절차대로 다시 한다.
2. **확인**

   ```powershell
   bun run check
   bun test src/state/queue-rules.test.ts
   bun --bun playwright test src/components/chat --grep queue
   ```

3. **검토 지점** `queue-rules.ts`의 전이 표를 사람이 읽는다. "멈춤"이 되는 경우와 "다시 보냄"이 되는 경우가 F-QUEUE-2와 같은지 본다.
4. **입력** 검토 프롬프트. 절은 "3.2절 F-QUEUE, 4.6절, 7.1절, 9.11절".
5. **입력** 반영 프롬프트.

## 프롬프트 0. 규칙 정하기

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 먼저 AGENTS.md와 docs/TASKS.md의 지금 상태를 읽고 AGENTS.md의 규칙을 따른다.
이번 단계는 12 대기열이다. 브랜치 stage/12-queue 를 main에서 만들고, 이 단계의 커밋은 모두 그 브랜치에 한다.
코드를 고치지 않는다. 대기열의 상태 규칙을 내가 정하도록 묻는다.
1. DESIGN 3.2절의 F-QUEUE 와 앞 단계의 스펙, 승인된 POLICY.md 를 읽고 표 둘을 만든다.
   확정된 것: 문서에 이미 정해져 있는 규칙과 그 위치.
   정해야 할 것: 질문, 추천, 이유. 예를 들면 답변 중 Enter 와 보내기 버튼, 중단과 실패 뒤의 대기열, 다른 채팅에서도 계속 보내는지, 삭제와 새로고침 뒤.
2. 정해야 할 것끼리, 또는 확정된 것과 부딪히는 곳이 있으면 따로 짚는다.
3. 표를 보이고 멈춘다. 내가 답하면 확정 표, 제약, 하지 않는 것을 docs/DECISIONS.md 에 "사람이 정함"과 날짜로 적고 커밋한다.
```

## 프롬프트 1. 구현

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 먼저 AGENTS.md와 docs/TASKS.md의 지금 상태를 읽고 AGENTS.md의 규칙을 따른다.
고칠 폴더에 POLICY.md가 있으면 먼저 읽는다. "승인"인 정책만 규칙이다.
DESIGN.md나 승인된 정책과 부딪히거나, 되돌리기 어렵거나 다른 단계에 걸리는 판단이 필요하면 고치기 전에 멈추고 규칙 ID, 이유, 권장안을 보고한다. 그 밖의 작은 판단은 정한 뒤 보고의 "정한 것"에 적는다.
테스트를 먼저 쓰고, 구현하기 전에 돌려서 실패하는 출력을 보인다. 그 실패가 고칠 결함 때문인지도 본다.
테스트의 전체 출력은 시각을 붙인 로그 파일로 보내고, 대화에는 마지막 요약과 실패만 보인다.
끝나면 AGENTS.md 12장의 형식으로 보고한다. 돌리지 않은 것과 확인하지 못한 것은 그렇다고 쓴다.

이번 단계: 12 대기열. 프롬프트 0에서 만든 브랜치 stage/12-queue 에서 이어서 한다.
DESIGN 3.2절의 F-QUEUE, 4.6절, 7.1절, 9.11절과 docs/DECISIONS.md 의 대기열 확정 표를 읽는다. 서버는 바꾸지 않는다.

1. 테스트 먼저
   - 모듈(state/queue-rules.test.ts): 상태(running, paused)와 항목 목록에 대한 전이.
     답변 중 보냄은 끝에 쌓는다. 연결이 닫히면 running 일 때 맨 앞을 꺼낸다. 중단과 실패는 paused 로 바꾸고 꺼내지 않는다.
     paused 에서 보냄은 끝에 쌓고 paused 를 유지한다. Send 는 running 으로 되돌리고 맨 앞을 꺼낸다. Clear 는 모두 비운다.
     항목 취소는 그 항목만 뺀다. duplicate_message 는 그 항목을 보낸 것으로 친다.
     전이 하나를 일부러 틀리게 바꿔 해당 테스트가 실패하는 것을 보고 되돌린다(변이 확인). 바꾼 것과 실패한 테스트 이름을 보고한다.
   - e2e(asUser fixture, [[mock:slow]]): 셋을 쌓으면 셋 다 순서대로 답을 받는다. 쌓는 동안 다른 채팅으로 가도 이어서 보낸다.
     멈추면 "N queued", Send, Clear 가 보이고, Send 로 이어지고, Clear 로 비워진다. 항목의 취소로 그것만 빠진다.
     셋을 차례로 보내는 동안 409 가 한 번도 없다(응답을 센다). 409 를 page.route 로 한 번 돌려주면 대기열이 멈추고,
     거절된 메시지는 뒤에 대기가 있으면 맨 앞으로, 없으면 입력창으로 간다. 빈 대기열은 멈춘 것으로 보이지 않는다.
     항목을 취소해 그 버튼이 사라지면 포커스가 이웃 항목이나 입력창으로 간다(DESIGN 3.5절).
   돌려서 실패하는 출력을 보인다.
2. 구현
   - state/queue-rules.ts: 위 전이를 순수 함수로(STATE-12).
   - state/chats.tsx: Thread 의 queue 와 queueState. 다음 항목은 sendMessage 의 루프가 끝나 연결이 닫힌 뒤에 보낸다.
     대기열 항목도 clientMessageId 를 만들 때 정하고, 다시 보낼 때 같은 값을 쓴다.
   - components/chat: queued-message(취소 버튼), 입력창 위의 대기열 안내. 답변 중에도 입력창을 열어 둔다.
   - 대기열은 메모리에만 있고 새로고침하면 사라진다는 것을 docs/DECISIONS.md 에 한 줄로 적는다(DESIGN 14장).
3. 확인: bun run check, 위 테스트, 10단계와 11단계의 e2e 가 그대로 통과하는지.
4. 작게 커밋한다.
```

## 막히면

- **두 번째 항목이 409 `response_in_progress`다.** 답변이 끝난 이벤트에서 다음을 보냈다. 연결이 닫힌 뒤에 보낸다. 서버는 저장과 잠금 해제를 끝낸 뒤 `[DONE]`을 쓴다(DESIGN 4.6절).
