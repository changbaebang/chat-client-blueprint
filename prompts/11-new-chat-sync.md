## 이 단계가 끝나면

- [ ] 홈 입력창에서 첫 메시지를 보낼 때 채팅이 생기고, 바로 보내고, 채팅 화면으로 간다. 홈을 열기만 해서는 채팅이 생기지 않는다.
- [ ] 만들기에 실패하면 입력이 그대로 남고 이유가 보인다.
- [ ] New chat 버튼과 `mod+Shift+O`가 홈으로 가서 입력창에 포커스를 준다.
- [ ] 답변의 `chat.updated`가 목록에 반영된다. 기본 목록이면 맨 위로, Today 그룹으로, 제목이 `null`에서 실제 제목으로. 답변 중 표시가 있다.
- [ ] 답변 중에 바꾼 이름이 되돌아가지 않는다(F-RENAME-2).
- [ ] 브라우저 탭 제목이 채팅 제목을 따른다.
- [ ] 행이 맨 위로 옮겨질 때 사이드바의 보던 위치가 튀지 않는다(세 엔진).

## 순서

1. **입력** 프롬프트 1.
2. **확인**

   ```powershell
   bun run check
   bun --bun playwright test src/components/home src/components/shell
   ```

3. **직접 확인** `bun run dev`로 띄우고, 사이드바를 중간쯤 스크롤한 채 아래쪽 채팅에서 답을 받는다. 그 행이 맨 위로 올라갈 때 보던 행들이 화면에서 튀지 않아야 한다.
   **이해 확인** README 6.11절로 "홈에서 Enter를 누른 뒤 사이드바에 새 행이 생기고 채팅 화면으로 갈 때까지"를 설명받고 `docs/READING.md`에 자기 말로 적는다.
   **화면 점검** 아래 "화면 점검" 절.
   **새 세션 시험(한 번)** 이 단계가 끝나면 새 세션에 "docs/TASKS.md의 다음 단계를 시작해줘. 규칙은 AGENTS.md에 있다." 한 줄만 준다.
   정책을 읽는지, 명세에 없는 판단에서 멈추는지, 테스트를 먼저 쓰는지 본다. 막힌 곳은 문서의 빈틈이니 문서를 고치고 기록한다. 시험이 끝나면 그 세션의 변경은 버린다.
4. **검토 지점** 새 채팅을 시작하는 기능 훅을 읽는다. 채팅 만들기, 빈 스레드를 `ready`로 두기, 이동, 보내기의 순서와, 만들기와 이동 사이에 메시지 읽기가 끼어들어 임시 메시지를 덮지 않는 이유를 짚을 수 있어야 한다.
5. **입력** 검토 프롬프트. 절은 "3.2절, 4.4절, 7.1절, 7.3절, 9.11절".
6. **입력** 반영 프롬프트.

## 막히면

- **새 채팅으로 이동한 직후 보낸 글이 사라졌다가 돌아온다.** 이동하자마자 채팅 화면이 메시지를 읽어 빈 목록으로 덮었다. 만들기 직후 그 스레드를 `ready`로 두어 열기가 다시 읽지 않게 한다.
- **`mod+Shift+O`가 브라우저의 북마크 관리자를 연다.** 키를 앱이 받아 `preventDefault`하는지 본다. 자동화의 키 입력은 브라우저 자체 단축키에 닿지 않으니, 실제 Chrome에서 직접 확인 목록으로 본다.
