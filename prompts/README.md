# 단계 프롬프트

Git만 설치된 Windows PC에서, 설계와 프롬프트만 있는 이 저장소 안에 [설계 문서](../docs/DESIGN.md)의 채팅 앱을 끝까지 만드는 18개 단계다. 설계, 프롬프트, 앱이 한 저장소에 있다. Bun 하나와 의존성 열 개로 만든다. 프롬프트만이 아니라 단계마다 사람이 무엇을 하고 무엇을 보는지까지 적었다. 설계에 담은 원칙과 반영한 곳은 [TASKS.md 6장](../TASKS.md#6-설계에-담은-원칙)에 있다.

## 2. 역할

| 역할 | 하는 일 |
| ---- | ------- |
| 사람 | 단계를 고르고 프롬프트를 붙인다. 제품 규칙과 새 기능의 상태 규칙을 정한다. 에이전트의 질문 중 결정할 것에 답한다. "검토 지점"과 `docs/READING.md`의 새 행을 직접 읽고 체크한다. 화면 점검의 캡처를 보고 체크하고, "직접 확인"을 손으로 본다. 정책을 승인한다. "반영해줘"를 말한다 |
| 구현 에이전트 | 테스트를 먼저 쓰고 실패를 보인다. 구현한다. 확인 명령을 돌리고 결과를 그대로 보고한다. 사람이 읽을 곳을 `docs/READING.md`에 더한다 |
| 검토 에이전트 | 새 대화에서, 가능하면 다른 모델로 검토 프롬프트를 받는다. 그 단계의 완료 조건을 기준으로 코드와 화면을 함께 본다. 파일을 고치지 않는다. 돌려 보지 않은 것은 "확인하지 못함"이다 |
| 지시 세션(선택) | 실행 세션의 보고를 읽고 다음 지시를 다듬는 대화. 나누면 실행 세션의 대화가 짧아진다. 나눴다면 17단계의 보고서에 그렇게 밝힌다 |

**나누는 법:** UI와 테스트는 에이전트가 쓰고, 상태와 전송은 사람이 인터페이스와 규칙을 정해 맡긴다. 사람은 읽고 설명한다. 붙이는 지시는 자기 말투로 고쳐도 된다. 범위만 지킨다.

**사람의 몫이 보이게:** 코드는 에이전트가 써도 규칙과 순서는 사람이 정했다는 것이 기록에 남아야 한다. 이렇게 한다.

1. **읽음 체크:** 단계마다 에이전트가 `docs/READING.md`에 읽을 곳을 더하고, 사람이 읽고 체크한다. 질문이 나올 핵심 15~20곳을 먼저 읽는다.
2. **이해 확인:** 10, 11단계에서 Enter부터 화면 갱신까지를 에이전트가 파일:줄로 설명하고, 사람이 자기 말로 한두 줄 적는다(6.11절). 면접 전이 아니라 만드는 동안 한다.
3. **손으로 고쳐 보기:** 한두 번은 6.4절의 위치 설명만 받고 사람이 직접 고친다.
4. **상태 규칙은 사람이:** 새 기능의 상태 규칙은 질문 목록에 사람이 답해서 정한다(12단계).
5. **그 자리에서 적기:** 따르지 않은 AI 제안과 사람이 새로 정한 규칙은 미루지 않고 적는다(6.6절). 17단계의 보고서가 이 목록을 쓴다.

**리뷰어 세션:** 단계가 끝날 때 앞 단계의 작업 세션이나 별도 세션에 6.2절의 검토를 준다. 앱을 띄워 흐름을 직접 따라가는 검토도 한다.

**새 세션 시험:** 11단계쯤에서 한 번, 문서만 아는 새 세션에 문서를 가리키는 짧은 지시만 준다. 정책을 읽는지, 명세에 없는 판단에서 멈추는지, 테스트를 먼저 쓰는지 본다. 막힌 곳은 문서의 빈틈이니 문서를 고치고 기록한다. 같은 지시를 작은 모델로 돌려 볼 수도 있다.

**다른 방식:** 사람이 코드를 직접 고치며 배우고 싶으면 구현 프롬프트 대신 6.4절의 "위치 설명" 틀로 고칠 곳만 받고 직접 고친다. 테스트는 에이전트가 쓴다.

## 3. 한 단계를 하는 순서

1. **사람** 단계 파일의 "이 단계가 끝나면"을 읽는다.
2. **사람** Claude Code를 이 저장소 폴더에서 새 세션으로 연다. 상위 폴더가 아니라 이 폴더 자체를 연다. 상위 폴더에서 열면 `CLAUDE.md`가 시작할 때 로드되지 않는다. 단계마다 새 세션이 좋다. 앞 단계의 대화가 판단을 끌고 가지 않고, 문서만으로 되는지 드러난다.
3. **입력** 단계의 "프롬프트 1"을 붙인다. 에이전트는 먼저 `docs/TASKS.md`의 지금 상태를 읽고(15단계부터는 `docs/Issues.md`도), 이 단계의 범위를 한 줄로 적는다.
4. **에이전트** 브랜치를 만들고, 테스트를 먼저 쓰고 실패를 보인 뒤, 구현하고 확인한다. 공용 부품을 먼저 고치고 그것을 쓰는 기능을 뒤에 한다. 하다가 찾은 다른 것은 바로 한 줄로 기록에 넘긴다.
5. **확인** 사람이 단계의 확인 명령을 PowerShell에서 직접 돌린다. 에이전트의 보고와 같은지 본다. 에이전트가 테스트를 돌리는 동안에는 돌리지 않는다(같은 포트를 쓴다).
6. **화면 점검** 화면 단계(04, 08, 09, 10, 11, 13, 14)는 6.12절의 화면 점검을 돌고, 사람이 캡처를 보고 체크한다.
7. **입력** 새 대화에서 6.2절의 검토 프롬프트를 붙인다.
8. **사람** "검토 지점"과 `docs/READING.md`의 새 행을 직접 읽고 체크한다. 검토의 지적을 받아들일지 정한다. 받아들이지 않은 것은 그 자리에서 6.6절로 적게 한다. 10, 11단계에서는 6.11절의 이해 확인도 한다.
9. **사람** 그 단계가 만든 `POLICY.md`를 읽고 승인하면 "승인"으로 바꾸게 한다.
10. **입력** "반영해줘"(6.5절). 합류 전 실행이 도는 동안에는 사람도 파일을 고치지 않는다.

## 4. 붙여넣기 규칙

- 코드 블록 안의 글을 그대로 붙인다. 자기 말투로 고쳐도 된다. 범위와 멈출 조건만 지킨다.
- 블록 안에는 ①② 같은 원문자와 화살표 같은 기호를 쓰지 않았다. 원문자는 붙여넣는 중에 깨질 수 있다. 고쳐 쓸 때도 `1.`, `(1)`, `1번`을 쓴다.
- 한글이 든 중괄호(`{브랜치}` 같은 것)만 사람이 채울 칸이다. 채우지 않은 칸이 남아 있으면 에이전트는 멈추고 무엇을 채울지 묻는다(AGENTS.md 1장). 코드의 중괄호(`{ user }`, `{20}`)는 칸이 아니다. 에이전트가 따를 이름 틀은 `<단계>`처럼 꺾쇠로 쓴다. "(블록 붙여넣기)" 같은 자리표시는 쓰지 않고 완성된 블록을 준다.
- 한 번에 프롬프트 하나를 붙인다. 앞 프롬프트의 보고를 읽은 뒤 다음을 붙인다.
- 테스트 결과를 붙일 때는 마지막 요약 줄과 실패 목록만 붙이고, 전체는 로그 파일의 경로로 준다. 세션 기록이 커지는 것을 막는다.
- 보낸 지시가 반영되어야 할 것이 보이지 않으면, 다시 보내기 전에 메시지가 실제로 전달됐는지(대화에 보이는지) 먼저 본다.
- 사람에게 주는 명령은 VS Code의 기본 터미널인 PowerShell의 문법으로 쓴다. 에이전트가 직접 돌릴 수 있는 것은 에이전트가 돌린다.

## 5. 모델과 사용량

- **구현:** 큰 모델이 안전하다. 10단계처럼 상태가 복잡한 단계는 특히 그렇다.
- **검토와 결함 찾기:** 관점과 확인 목록을 주면 작은 모델도 잘 찾는다. 한 덩어리 프롬프트보다 관점별 확인 목록이 더 많이 찾는다.
- **병렬:** 하위 에이전트는 한 번에 4개까지 띄운다. 한꺼번에 많이 띄우면 사용 한도에 금방 걸린다.
- **진행 방식:** 기본은 묶음마다 멈춰 사람이 승인한다. 빠른 모드는 승인 없이 이어 가고 정할 것만 멈춘다. 빠른 모드의 묶음 확인은 Chromium만 하고, 세 엔진과 전체는 반영 직전에 돈다. 빠른 모드에서도 새 테스트의 구현 전 실패(그 파일만)와 핵심 변이 한두 개는 그대로 한다. 이 둘을 빼면 테스트가 무엇을 지키는지 알 수 없다. 에이전트는 `docs/TASKS.md` 맨 위의 "진행 방식" 줄을 따른다(DESIGN 10.5절). 바꾸려면 그 줄을 고친다.
- **사용량 중단:** 5시간 한도나 결제 문제로 중간에 끊길 수 있다. 상태는 대화가 아니라 저장소에 남긴다(작은 커밋, `docs/TASKS.md`의 메모). 다시 시작할 때는 6.10절을 붙인다.
- **잰 시간:** e2e 시간은 워커 수에 따라 크게 달라진다. 이 블루프린트는 처음부터 워커별 서버다(DESIGN 11.4절). 단계마다 잰 시간을 `docs/test-plan.md`에 더한다.

## 6. 공통 틀

### 6.1 구현 프롬프트의 머리말

모든 단계의 "프롬프트 1"이 이 여섯 줄로 시작한다. 단계 파일에 이미 들어 있다. 각 줄이 부르는 규칙은 `AGENTS.md`에 있다(DESIGN 10.1절). 머리말은 그 규칙을 부르기만 한다.

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 먼저 AGENTS.md와 docs/TASKS.md의 지금 상태를 읽고 AGENTS.md의 규칙을 따른다.
고칠 폴더에 POLICY.md가 있으면 먼저 읽는다. "승인"인 정책만 규칙이다.
DESIGN.md나 승인된 정책과 부딪히거나, 되돌리기 어렵거나 다른 단계에 걸리는 판단이 필요하면 고치기 전에 멈추고 규칙 ID, 이유, 권장안을 보고한다. 그 밖의 작은 판단은 정한 뒤 보고의 "정한 것"에 적는다.
테스트를 먼저 쓰고, 구현하기 전에 돌려서 실패하는 출력을 보인다. 그 실패가 고칠 결함 때문인지도 본다.
테스트의 전체 출력은 시각을 붙인 로그 파일로 보내고, 대화에는 마지막 요약과 실패만 보인다.
끝나면 AGENTS.md 12장의 형식으로 보고한다. 돌리지 않은 것과 확인하지 못한 것은 그렇다고 쓴다.
```

### 6.2 검토

```text
이 저장소의 브랜치 {브랜치}를 검토한다. 파일을 고치지 않는다.
기준은 docs/DESIGN.md의 {절}, 바뀐 폴더의 POLICY.md, AGENTS.md, 그리고 이 단계의 완료 조건이다.
git diff main...HEAD 를 읽고, 필요하면 파일을 연다. 화면 단계면 앱을 띄워 흐름을 직접 따라간다.

1. 첫 줄에 "통과" 또는 "통과 아님"을 쓴다.
2. 통과가 아니면 어느 파일의 몇 번째 줄이 어느 기준(규칙 ID나 절 번호)에 어긋나는지 쓴다.
3. 이 단계의 완료 조건 중 테스트가 없는 것을 쓴다.
4. 구현 전에 실패한 기록이 없거나, 단언이 약해서 실패를 잡지 못할 것 같은 테스트를 쓴다.
5. 통과하도록 바뀐 테스트가 기대를 낮춘 것은 아닌지 본다. test.fail 이나 조건 제외로 실패를 가렸는지 본다.
6. 화면 단계면 docs/evidence/ui/{단계}/ 의 캡처를 보고 DESIGN 3.7절의 UX 기준에 어긋나는 것을 쓴다.
7. 돌려 보지 않고 판단한 것은 "확인하지 못함"으로 쓴다.
8. 기준과 상관없는 취향은 쓰지 않는다. 중요한 것부터 최대 10건.
```

### 6.3 막혔을 때

```text
{단계} 단계에서 막혔다. 고치지 말고 원인만 짚는다.
먼저 실패를 나눈다.
- 시간 초과나 연결 오류: 그 파일만 한 번 다시 돌린다. 다시 나면 멈추고 보고한다.
- 단언 값이 어긋남: 다시 돌리지 않는다. 원인부터 찾는다. 반영은 미룬다.
- already used: 다른 실행이 같은 포트를 쓰는 중이다. 끝날 때까지 기다린다.
그다음 아래 로그와 git diff 를 보고, 어느 파일의 어느 줄이 어떤 경우를 놓쳤는지 말한다.
원인을 확인하지 못했으면 "확인하지 못함"이라고 쓰고, 확인하려면 무엇을 돌려야 하는지 쓴다.

명령: {돌린 명령}
로그: {로그 파일 경로}
요약: {마지막 요약 줄과 실패한 테스트 이름}
```

사람은 가설("아마 X 때문")보다 기준(위의 세 갈래)을 준다. 가설을 주면 에이전트가 그쪽으로 끌려간다. 원인이 흐리면 6.9절의 관찰 지시로 바꾼다.

### 6.4 위치 설명

사람이 직접 고칠 때 쓴다.

```text
아래 작업을 내가 직접 고치려 한다. 고치지 말고 설명만 한다.
1. 어느 파일의 어느 함수, 몇 번째 줄을 고쳐야 하는지
2. 왜 그런지, 어떤 입력에서 드러나는지
3. 함께 봐야 하는 다른 파일과 그 폴더의 POLICY.md 규칙
4. 고친 뒤에 돌릴 테스트

작업: {완료 조건이나 결함}
```

### 6.5 반영

```text
반영해줘.
```

이 한마디면 된다. 절차는 `AGENTS.md` 5장이 가리키는 DESIGN 10.5절에 있다. 지시에 같은 말을 되풀이하지 않으려고 절차를 문서로 옮겼다. 처음 몇 번은 보고가 아래 순서와 같은지 본다.

1. 작업 트리가 깨끗한지 본다. 아니면 멈추고 무엇이 남았는지 보인다.
2. 문서의 상태와 해시가 커밋된 코드와 맞는지 대조한다.
3. 합류 전 확인을 돌린다: `bun run check`, `bun run test:e2e`, `bun run test:e2e:build`. 아직 없는 스크립트는 "해당 없음"으로 적는다. 3분이 넘으면 백그라운드로 돌리고, 예상 시간을 먼저 말한 뒤 로그 파일을 보며 5분마다 진행을 짧게 보고한다. 도는 동안 아무도 파일을 고치지 않는다. 하나라도 실패하면 멈추고 6.3절의 갈래로 보고한다.
4. 합류 전 실행 뒤에 앱 코드가 바뀌었으면 3을 다시 돈다. 테스트 파일만 바뀌었으면 그 파일만 다시 돌린다.
5. 기능 브랜치에 선 채로 `git fetch . {브랜치}:main`, 그다음 `git switch main`. fast-forward가 안 되면 멈춘다.
6. `docs/TASKS.md`의 이 단계를 "반영"으로 바꾸고, `main` 해시와 마지막 전체 실행의 결과(건수, 시간)를 적어 커밋한다.
7. `main`의 해시를 보고한다. 브랜치는 지우지 않는다. 푸시하지 않는다.
8. 진행 보고를 되풀이하고 있었으면 멈춘다고 말한다.

**가벼운 주기(선택):** 시간이 모자라면 `docs/TASKS.md` 맨 위의 진행 방식 줄에 "가벼운 주기"를 넣는다. 그러면 반영마다 `bun run check`와 바뀐 영역의 e2e(새 테스트는 세 엔진)만 돌고, Chromium 전체는 브랜치 한두 개마다, 세 엔진 전체와 build는 마일스톤에 돈다. 전체 실행 없이 반영한 것은 `docs/TASKS.md`에 적는다. 기본은 위의 전체 절차다.

### 6.6 따르지 않은 제안 적기

```text
방금 검토의 {번호}번 지적은 따르지 않는다. 이유: {이유}
docs/DECISIONS.md 끝의 "따르지 않은 AI 제안" 표에 날짜, 제안, 이유, 출처(어느 세션의 어느 보고)를 한 줄로 더하고 커밋한다.
```

미루지 않고 그 자리에서 적는다. 사람이 새로 정한 규칙은 `AGENTS.md` 9장의 방식대로 그 자리에서 규칙 문서에 더하고 "사람이 정함"과 날짜를 붙인다.

### 6.7 보고

`AGENTS.md` 12장의 틀이다. 보고가 이 틀을 벗어나면 붙인다.

```text
보고를 이 틀로 다시 써줘. 없는 항목은 "없음"이라고 쓴다.
1. 결과 그대로: 돌린 명령, 마지막 요약 줄, 종료 코드, 로그 파일 경로
2. 구현 전 실패: 새 테스트마다 실패한 출력 한 줄과, 그 실패가 고칠 결함 때문인지
3. 실패와 원인: 아직 남은 실패와 6.3절의 어느 갈래인지
4. 정한 것: 지시에 없어서 정한 것과 이유
5. 지시와 다르게 한 것: 무엇을, 왜
6. 확인하지 못한 것: 돌리지 않았거나 볼 수 없었던 것
7. 직접 확인 필요: 앞 보고에 이어 번호를 붙인다. 절차와 기대 결과까지
8. 정해 주실 것: 권장안과 이유
9. 읽을 곳: docs/READING.md 에 더한 행
```

### 6.8 선언 지시

여러 묶음으로 이어지는 작업(15, 16단계, 큰 기능)은 먼저 기준을 문서에 옮기고, 묶음마다의 지시는 그 절을 가리키기만 한다. 지시가 짧아지고, 새 세션도 같은 기준으로 일한다.

```text
이번 작업은 여러 묶음으로 나뉜다. 시작하기 전에 기준을 문서에 옮긴다.
1. 아래 기준을 docs/TASKS.md 의 "{작업 이름}" 절에 선언형으로 옮긴다. 목표, 하지 않는 것, 묶음 목록, 묶음마다 끝나는 조건.
2. 옮긴 절을 보이고 멈춘다. 내가 승인하면 커밋한다.
3. 그 뒤의 지시는 "{작업 이름} 절의 묶음 {번호}"처럼 절을 가리키기만 한다. 묶음마다 볼 곳만 덧붙인다.

기준:
{목표, 하지 않는 것, 묶음}
```

### 6.9 관찰 지시

원인이 흐릴 때 고치기 전에 쓴다.

```text
고치지 말고 관찰만 한다. 시간은 {몇}분까지다.
1. 앱 코드는 그대로 둔다. 임시 기록 코드가 필요하면 넣을 곳을 먼저 말한다.
2. {재현 조건}에서 {보고 싶은 것}을 기록한다. 세 엔진에서 각각 {횟수}번.
3. 판정한다.
   테스트 문제: 테스트가 실제 사용자의 경로와 다르다. 어떻게 다른지 쓴다.
   앱 문제: 앱이 그 조건에서 틀린다. 어느 파일 몇 번째 줄인지 쓴다.
   판단 불가: 시간 안에 가르지 못했다. 멈추고 무엇을 더 보면 되는지 쓴다.
4. 임시 코드와 임시 파일을 지우고 git status 와 git diff 가 비었는지 보인다.
재현 테스트가 고치기 전에 실패하지 않으면 고치지 말고 멈춘다.
```

### 6.12 화면 점검

화면 단계(04, 08, 09, 10, 11, 13, 14. 12를 하면 12도)에서 기능의 확인이 끝난 뒤, 검토 전에 한다. 기준은 [DESIGN 3.7절](../docs/DESIGN.md#37-화면-품질)이다. 단계 파일의 "화면 점검" 절에 그 단계의 흐름을 채운 블록이 있다.

```text
이 단계의 화면 점검을 한다. 기준은 docs/DESIGN.md 3.7절이다. 앱 코드는 고치지 않는다.
1. SCREENS_STAGE={단계} bun run test:screens 를 돌려 docs/evidence/ui/{단계}/ 에 캡처를 남긴다.
   이 단계에서 생긴 화면과 상태가 @screens 에 없으면 먼저 더한다.
2. 처음 쓰는 사람의 눈으로 흐름을 따라간다: {이 단계의 흐름}.
   밝은 테마와 어두운 테마, 창 1280x800, 1024x700, 1280x480.
3. docs/evidence/ui/{단계}/CHECK.md 를 만든다. UX-1부터 UX-10까지 행마다 캡처 파일, 본 것,
   판정(맞음, 고칠 것, 사람이 볼 것)을 쓰고, 끝에 사람이 체크할 빈 칸을 둔다.
4. 같은 상황의 안내 문구를 표로 모은다(UX-7).
5. 일반 AI 에이전트 웹앱과 다르게 한 곳은 docs/evidence/ui/compare.md 에 이유와 함께 적는다(UX-2).
   일반 AI 에이전트 웹앱의 화면은 사람이 직접 찍어 docs/evidence/ui/reference/ 에 넣은 것만 쓴다.
6. "고칠 것"을 목록으로 보이고 멈춘다. 이 단계에서 고칠지 15단계로 넘길지는 내가 정한다.
```

**사람** 캡처를 직접 열어 보고 `CHECK.md`의 빈 칸에 체크한다. 캡처만으로 모자라면 앱을 띄워 그 흐름을 10분쯤 직접 써 본다. 체크하지 않은 단계는 반영하지 않는다(UX-10). 고치기로 한 것은 같은 단계에서 고치고 캡처를 다시 찍는다.

## 7. 기록

- **작업의 기록은 커밋이다:** 세션 로그는 저장소에 넣지 않는다. 테스트의 전체 출력은 대화에 붙이지 않고 로그 파일로 보낸다.
- **증거:** 화면 캡처, 측정표, 직접 확인 기록은 임시 폴더가 아니라 `docs/evidence/`에 둔다.
- **단계 상태:** 앱의 `docs/TASKS.md`가 단계마다 상태와 `main` 해시를 갖는다. 상태는 대기, 진행, 명세, 반영, 안 함이다. `main`에는 "진행"이 없다(AGENTS.md 14장).
- **두 TASKS:** 루트의 `TASKS.md`는 이 포트폴리오의 작업 목록이라 사람이 관리한다. `docs/TASKS.md`는 앱의 단계 상태라 에이전트가 고친다.
- **막힌 곳:** 프롬프트가 모자라 막힌 곳은 이 폴더의 단계 파일 "막히면"에 되돌려 적는다. 두 번째 실행이 첫 번째보다 덜 막히는 것이 목표다.
