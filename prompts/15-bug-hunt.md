# 15. 결함 찾기

기능이 다 생긴 뒤 결함과 개선 후보를 찾는 단계다. 코드를 고치지 않는다. 결과는 `docs/Issues.md`(고장)와 `docs/Improvements.md`(바라는 동작과 다듬기) 둘이다.

한 에이전트에게 "전부 찾아라"고 하지 않고, 관점을 열 개로 나눠 따로 맡긴다. 화면 관점이 맨 앞이다(DESIGN 3.7절). 관점과 확인 목록을 주면 작은 모델도 잘 찾는다.

| 항목 | 값 |
| ---- | -- |
| 브랜치 | `stage/15-bug-hunt` |
| 선행 | 14 |
| 읽을 문서 | DESIGN 전체, 모든 `POLICY.md`, `docs/test-plan.md` |
| 고칠 폴더 | `docs/Issues.md`, `docs/Improvements.md`만 |
| 쓸 스킬 | (설치하면) `bug-triage`, `critical-review` |

## 이 단계가 끝나면

- [ ] 관점 열 개(화면이 먼저)의 리뷰가 각각 따로 돌았다. 어느 모델로 돌았는지 기록했다.
- [ ] 사람이 직접 20분 써 보고 본 것을 적었다.
- [ ] 세 엔진 전체 e2e와 `data:check`를 돌린 결과가 있다.
- [ ] 결함마다 사람이 그 줄을 열어 확인했고, 확인 수준(실행 확인, 코드상 확실, 브라우저 확인 필요)을 붙였다. 설명과 코드가 다른 지적은 버렸다.
- [ ] 같은 결함을 하나로 묶었다.
- [ ] 지적마다 재현으로 갈랐다(유효, 부분, 무효, 미확인). "재현 안 됨"은 조건을 갖춘 뒤에만 썼다. 계산으로 기각한 것에는 실물로 다시 볼 조건이 있다.
- [ ] 결함은 `docs/Issues.md`, 개선 후보는 `docs/Improvements.md`에 있다. 두 표 모두 출처 열(사람 제안, 직접 사용, 벤치마크, AI 지적, 테스트)이 있어 사람이 낸 것만 걸러 볼 수 있다.
- [ ] `docs/Issues.md`에 결함마다 ID, 제목, 위치, 재현, 영향, 심각도, 확인 수준, 찾은 곳(관점이나 사람), 결정(고친다, 안 고친다, 확인 후 판단), 테스트 층이 있다.

## 순서

1. **사람** 20분 동안 앱을 실제 사용자처럼 쓴다. 아래 "직접 써 보기"를 참고한다. 본 것을 메모장에 적는다.
2. **입력** 프롬프트 1(기계로 돌리는 확인).
3. **입력** 프롬프트 2(관점별 리뷰). 하위 에이전트로 병렬로 돌리거나, 프롬프트 3을 관점마다 새 대화에 붙인다.
4. **사람** 지적마다 적힌 줄을 열어 본다. 확인 수준을 붙이고, 설명과 코드가 다르면 버린다. 작은 모델일수록 이런 지적이 섞여 나온다.
5. **입력** 프롬프트 4(묶고 기록하기). 1번의 메모와 4번에서 살린 지적을 붙인다.
6. **사람** `docs/Issues.md`와 `docs/Improvements.md`의 결정 열을 정한다. 개선 후보도 모두 "한다"나 "안 함"으로 정한다. 정하지 않은 것이 남으면 17단계가 끝나지 않는다. 기준: 데이터를 잃거나 틀리게 보이는 것, 멈추는 것, 남의 데이터가 보이는 것은 고친다. 나머지는 비용과 영향으로 정한다.
7. **입력** 반영 프롬프트.

### 직접 써 보기

- **처음 쓰는 사람처럼:** 문서를 보지 않고 10~20분 쓴다. 동작은 맞는데 거슬리는 것(기다리게 하는 곳, 결과를 알리지 않는 동작, 튀는 화면, 어색한 문구)을 적는다.
- **직접 비교:** 일반 AI 에이전트 웹앱(Claude 웹이나 ChatGPT)에서 같은 일을 해 보고 화면을 녹화한다. 답변 중에 보내기, 고정, 찾기, 작은 창, 어두운 테마. 검색으로 채우지 말고 직접 써 본 것만 적는다. 결과는 결함이 아니라 개선 후보다.
- 새 사용자를 만들고, 채팅 다섯 개를 만들고, 각각에 두세 번 보낸다. 긴 답(`[[mock:long]]`)을 하나 받는다.
- 답변 중에 멈추고 바로 보낸다. 답변 중에 다른 채팅으로 가고 돌아온다. 답변 중에 이름을 바꾸고 지운다.
- 탭 두 개로 같은 채팅을 연다. 한쪽에서 보내고 다른 쪽을 새로고침한다.
- 다른 사용자로 바꾼다. 다시 앞 사용자로 돌아온다.
- 창 높이를 줄인다. 사이드바를 접고 펴고 너비를 바꾼다. 어두운 테마로 바꾼다.
- 서버를 끄고 써 본다. 다시 켠다.
- 답변 중에 서버를 Ctrl+C로 끄고 다시 켠 뒤 그 채팅을 연다.

## 프롬프트 1. 기계로 돌리는 확인

```text
이 저장소의 결함 찾기 단계다. 브랜치 stage/15-bug-hunt 를 main에서 만든다. 코드를 고치지 않는다.

1. 다음을 돌리고 각각의 마지막 줄과 종료 코드를 표로 보인다.
   bun run check, bun run test:e2e:all, bun run build, bun run test:e2e:build, bun run data:check
2. 실패한 테스트가 있으면 테스트 이름, 엔진, 오류의 첫 줄을 적는다. 다시 돌려 통과시키지 않는다.
   연결 거부나 시간 초과는 그 파일만 한 번 다시 돌리고 두 결과를 모두 적는다.
3. bun run check:imports 와 tsc 가 잡지 않는 정책 위반을 찾는다. 각 POLICY.md 의 "확인 방법"이 "리뷰"인 규칙마다 코드를 검색해 어긋난 곳을 적는다.
   예: RDB-2(prepare 안의 템플릿 문자열), DOM-5(domain 의 Date.now 와 Math.random), LIB-4(lib/router.tsx 밖의 history 와 location).
4. 결과를 docs/Issues.md 에 쓰지 말고 보고만 한다. 4번 프롬프트에서 합친다.
```

## 프롬프트 2. 관점별 리뷰 (하위 에이전트로)

```text
이 저장소의 결함 찾기 단계다. 코드를 고치지 않는다.
아래 관점 열 개마다 하위 에이전트를 하나씩 띄운다. 0번을 먼저 띄운다. 한 번에 4개까지만 띄우고, 끝나면 다음 4개를 띄운다.
하위 에이전트에게는 프롬프트 3의 공통 부분에 관점 하나와 그 확인 목록을 붙여 준다. 모델은 {작은 모델 이름, 예: haiku}를 쓴다.
하위 에이전트의 결과를 고치거나 합치지 말고, 관점별로 그대로 보인다. 맨 끝에 관점마다 몇 건이었는지 표로 보인다.

관점과 확인 목록:
0. 화면과 처음 쓰는 사람의 흐름: docs/evidence/ui/ 의 캡처와 CHECK.md, DESIGN 3.7절의 UX 기준. 무엇을 눌러야 할지 모르는 화면.
   결과를 알리지 않는 동작. 정렬, 간격, 잘림, 겹침, 튀는 화면, 두 테마의 차이, 긴 값. 같은 상황의 다른 문구. compare.md 에 적은 이유가 맞는지.
1. 브라우저 차이: 플랫폼 판별이 Chrome, Safari, Firefox에서 받는 값. 클릭하면 포커스가 간다고 가정하는 코드. ISO가 아닌 문자열을 Date에 넘기는 곳.
   event.key 로만 비교하는 키. 한글 조합 중 Enter. 일부 엔진만 지원하는 CSS. 스크롤 고정과 휠 처리.
2. 비동기와 경합: 상황이 바뀐 뒤 늦게 온 응답을 버리는지. 스트림, 타이머, 리스너를 정리하는지. 실패를 삼키는 catch.
   같은 작업이 두 번 시작될 수 있는 곳. 멈춤과 삭제가 서버의 작업까지 끝내는지. 사용자가 바뀔 때 진행 중인 것이 남는지.
3. 데이터와 목록: 페이지가 추가와 삭제 뒤에도 빠짐과 겹침 없이 이어지는지. 고정과 날짜 그룹과 순서가 서버와 맞는지.
   같은 데이터를 반복해서 요청하는 곳. 서버 값을 화면용으로 바꾸는 코드가 모든 값(null, 빈 글, 아주 긴 글)을 다루는지.
4. 접근성과 키보드: role 을 붙인 요소가 그 역할의 키보드 동작을 하는지. 열고 닫을 때 포커스. 키보드만으로 다 되는지.
   대비, 동작 줄이기, 스크린 리더가 읽을 이름과 상태.
5. 오류 처리와 API 계약: API를 부르는 곳마다 실패하면 무엇이 보이는지. docs/API.md 의 한도(글자 수, 고정 수, 메시지 수)를 클라이언트가 다루는지.
   서버가 4.7절의 코드를 정말 그 상태로 내는지. 이상한 주소, 빈 값, 아주 긴 값.
6. 사용성과 성능: 문구, 스크롤 위치, 결과를 알리지 않는 동작, 화면에 남는 UI. 키를 누르거나 포인터를 움직일 때마다 일어나는 무거운 일.
   조각마다 다시 그려지는 범위. 실수로 데이터를 날릴 수 있는 조작.
7. 데이터 일관성과 저장소: DESIGN 5.4절의 쓰기 순서를 어기는 곳. 두 저장소 중 하나만 바뀌고 끝날 수 있는 경로. 잠금을 풀지 않는 경로.
   문서 잠금 밖의 읽기나 쓰기. 다시 시도하지 않는 파일 쓰기. 복구가 놓치는 어긋남. 요약을 +1로 쓰는 곳.
8. 보안과 사용자 경계: 소유권을 보지 않는 경로. 남의 채팅이 404가 아닌 곳. 로그에 남는 본문.
   HTML로 들어가는 사용자 글. 경로로 쓰이는 입력. Origin과 Host 검사를 지나치는 경로. 사용자를 바꾼 뒤 남는 데이터. X-User-Id 없이 닿는 경로.
9. 테스트 점검: 구현 전 실패를 본 적이 없는 테스트. 고정 대기를 쓰는 곳(지울 것, 신호로 바꿀 것, 남길 이유가 있는 것으로 나눈다).
   빈 통과 위험(세는 대상이 그려졌다는 단언 없이 0을 기대하는 렌더 횟수 테스트). 공용 데이터나 다른 테스트의 데이터에 기대는 테스트.
   끝에 끊지 않는 page.route. 여럿을 잡을 수 있는 선택자. 통과하도록 기대를 낮춘 테스트.
```

## 프롬프트 3. 관점 하나 (새 대화마다)

하위 에이전트를 쓰지 않을 때, 관점마다 새 대화에 이 글과 관점 하나를 붙인다.

```text
이 저장소는 docs/DESIGN.md의 채팅 앱이다. 코드를 점검해 결함을 찾는다. 파일을 고치지 않는다.
먼저 docs/DESIGN.md, docs/API.md, 그리고 바뀐 폴더의 POLICY.md 를 읽고, shared/, server/, src/ 의 코드를 읽는다.
DESIGN.md의 "하지 않는 것"(1.3절)과 "알려진 한계"(14장)에 있는 것은 결함이 아니다.

이번 점검의 관점: {관점 이름}
이 관점에서 특히 다음을 확인한다.
{확인 목록}

결함마다 다음을 적는다.
- 제목: 한 문장
- 파일: 저장소 루트부터의 경로와 줄 번호
- 재현: 무엇을 하면 무엇이 잘못되는지. 재현할 수 있을 만큼 구체적으로
- 영향받는 엔진: Chromium, Firefox, WebKit, 서버
- 심각도: 상(데이터가 틀리거나 사라지거나, 남의 데이터가 보이거나, 멈춤), 중(동작은 하지만 눈에 띄게 불편하거나 낭비), 하(다듬기)
- 근거: "코드를 읽어서" 또는 "직접 실행해서". 확신이 없으면 "확인 필요"를 붙인다

규칙:
- 코드를 실제로 읽고 확인한 것만 적는다. "오류 처리를 더하면 좋다" 같은 일반론은 적지 않는다.
- 중요한 것부터 최대 12건.
```

## 프롬프트 4. 묶고 기록하기

```text
결함 찾기의 결과를 docs/Issues.md 와 docs/Improvements.md 로 합친다. 코드를 고치지 않는다.
입력은 셋이다: 프롬프트 1의 보고, 내가 살린 관점별 지적(아래), 내가 직접 써 보고 비교한 메모(아래).

1. 지적마다 재현으로 가른다: 유효, 부분, 무효, 미확인. 재현 안 됨은 조건을 갖췄는지 확인한 뒤에만 쓴다.
   이상한 측정값은 측정 방법부터 의심한다. 계산으로 기각한 것에는 실물로 다시 볼 조건(어느 단계, 무엇으로)을 적는다.
2. 고장은 Issues, 바라는 동작과 다듬기는 Improvements 로 나눈다. 직접 비교에서 나온 것은 Improvements 다.
3. 같은 것을 하나로 묶는다. 묶은 것은 찾은 곳을 모두 적는다(예: 관점 2, 관점 7, 사람).
4. Issues 의 열: ID(BUG-01부터), 제목, 위치, 재현, 영향, 심각도, 판정, 확인 수준, 출처, 찾은 곳, 선행, 결정, 테스트 층, 다시 볼 조건.
   Improvements 의 열: ID(IMP-01부터), 제목, 바라는 동작, 근거, 출처, 예상 시간, 결정.
   출처는 사람 제안, 직접 사용, 벤치마크, AI 지적, 테스트 중 하나다. 선행은 먼저 끝나야 하는 결함이나 단계다.
   확인 수준은 내가 붙인 값을 쓴다. 예상 시간은 비교용이라 나중에 바꾸지 않는다.
   결정은 "미정"으로 두고, 심각도 상은 "고친다(제안)"로 둔다. 테스트 층은 DESIGN 11.1절의 기준으로 제안한다.
5. 심각도 순으로 정렬한다. 같은 심각도에서는 고치는 비용이 작은 것부터. 화면에 걸린 것은 UX-ID 를 붙인다.
6. 맨 위에 요약 표(심각도별 수, 출처별 수, 관점별로 낸 수와 산 수)를 둔다.
7. "docs: list the issues and improvements found by lens review and manual use" 로 커밋한다.

살린 지적:
{붙여넣기}

직접 써 보고 비교한 메모:
{붙여넣기}
```

## 막히면

- **하위 에이전트가 사용 한도에 걸린다.** 한 번에 4개, 작은 모델을 지킨다. 그래도 걸리면 관점을 둘씩 나눠 다른 시간에 돌린다.
- **지적이 일반론뿐이다.** 그 관점의 확인 목록을 빠뜨리고 붙였는지 본다. 확인 목록이 있을 때와 없을 때 찾는 수가 크게 다르다(README 5장).
